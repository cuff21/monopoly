# Gen6 Policy Schema 1 Specification

**Status:** Normative Schema 1 contract; implementation must satisfy the required tests listed below.

**Purpose:** This is the authoritative source for Gen6 observation, network, action, training, resource, persistence, and test requirements. [Structured_Board_Plan.md](Structured_Board_Plan.md) owns the overall migration roadmap and links here for Gen6 specifics; it must not redefine this contract.

## Compatibility and Board Support

Schema 1 identifies the complete policy contract: tile/per-seat/global feature meanings and normalization, layer dimensions and activations, named tensor ordering, action heads and trade semantics. Schema compatibility is determined solely by an exact `schemaVersion` match, independently of tensor count or optimizer metadata. A matching version does not make malformed data usable: validate the exact Schema 1 format, tensor names, shapes, and counts before inference. Reject 126-, 146-, and 147-input policies, all saved NEAT populations/genomes, interim data, and the legacy Gen6 localStorage keys `gen6Population` and `gen6Champion` without importing, migrating, or warm-starting them. Do not infer compatibility from input count. Do not treat the unrelated `gameHistory` key as Gen6 data.

The policy accepts any positive-size board satisfying the Board contract, subject to a configurable operational memory budget; resource-budget failures are not schema incompatibilities. Features use board kinds, game state, and circuit traversal values, never edition IDs, square/group IDs, labels, colors, DOM order, or storage position. Tile IDs identify the selected engine action only after scoring and never affect its score.

## Observation

Each observation is a variable-length array of 50-feature tile records, eight seat records (48 scalar values), 13 global values, a 16-wide context embedding, and context-specific data. The context ID order is fixed: 0 acquire, 1 auction, 2 jail, 3 property management, 4 debt resolution, 5 propose trade, 6 respond to trade. Do not append a context one-hot or numeric context ID to the observation; the ID selects the legal output-head schema and its learned 16-wide embedding is the only context identity feature supplied to the attention/trunk. Single-match observations contain only actual tiles; batched tile padding is masked in pooling and attention.

### Seat and Global Features

`Board.rules` contains edition base values for `startSalary`, `bailAmount`, `houseTotal`, and `hotelTotal`. Each Game owns a private Board copy; match setup may override these values on `Game.state.board.rules`. Validate the effective per-game values by the same constraints as the edition base values: `startSalary`, `houseTotal`, and `hotelTotal` are positive finite integers, and `bailAmount` is a nonnegative finite integer. Missing or invalid base/effective values reject Board or match setup; the policy encoder never supplies defaults. The effective `Game.state.board.rules` values are authoritative for that match and are the source of Gen6 global features. Available-house and available-hotel fractions are current available supply divided by the corresponding effective Board rule total. Global house and hotel total features remain normalized by 32 and 12 respectively. Training and validation matches use edition base values unless a scenario explicitly supplies overrides. Match overrides are not persisted and never affect another Game or the registered edition.

Each of eight seat records contains, in order: active-seat mask, deciding-seat flag, cash, get-out-of-jail card count, in-jail flag, jail turns. Seat slots are immutable original one-based player seats, not compacted active-roster indices; elimination leaves that seat inactive and zeroes its other features. The deciding-seat flag and owner-seat feature use the same stable seat ordinal. Normalize cash with the monetary scale above, card count as unclamped `log1p(count)`, and jail turns by 3; card counts must be finite nonnegative integers. Clamp all bounded values. Seats beyond the starting player count and eliminated seats are all zero; the active-seat mask is authoritative. Player IDs are not encoded.

Global values are exactly 13, in order: `log1p(tileCount)` (unclamped), `auctionEnabled`, `freeParkingTaxes`, Free Parking pot, available-house fraction, available-hotel fraction, start salary, bail amount, configured house total, configured hotel total, remaining horizon fraction, last dice total, signed context amount. Normalize money with the monetary scale above; supply by configured totals; house/hotel totals by 32/12; horizon by configured match-turn limit; dice by 12; signed context amount by the monetary scale and clamp `[-1,1]`. Context amount is current bid for auction, outstanding debt for debt resolution, incoming signed cash amount from the deciding player's perspective for respond-to-trade, and zero for all other contexts. Jail-card transfer counts are context-specific trade data, not global features; encode given and received counts as specified in the context payload manifest. The seven-way context identity is only in the context embedding. Context and global meanings are frozen by Schema 1.

## Network

Use fixed dimensions for every board:

- Shared tile encoder: `50 -> 32 ReLU -> 32 ReLU`, applied with identical weights to every tile.
- Board readout: masked mean, masked max, and 32-wide attention-weighted sum over tile embeddings. Every actual tile is included; only padded batch positions are masked. Action legality masks do not affect board pooling.
- Attention query: learned linear `109 -> 32` projection, with no activation, of the concatenated 16-wide context embedding, 61 global/per-seat values, and 32-wide target-tile embedding; use an all-zero target embedding when no target exists. For each tile embedding `h`, compute the attention logit as `dot(h, query) / sqrt(32)`.
- Context embedding: 16 values; global and per-seat inputs have fixed shape independent of active player count. The attention projection input is 109 values.
- Trunk: concatenate three 32-wide pooled tile vectors, 61 global/per-seat values, and the 16-wide context embedding (173 values); apply `173 -> 64 ReLU -> 64 ReLU`.
- Candidate scorer: shared dot-product score of tile embedding and projected trunk, plus operation embedding/bias. Candidate identity is not a scoring feature.
- Heads: sigmoid for Bernoulli and nonnegative scalar outputs; tanh for the signed trade-cash fraction; masked softmax for categorical choices. Trade-asset inclusion uses one independently masked Bernoulli output per legal asset candidate, with shared scoring parameters.

All policy parameters, observation inputs, and stored activations are Float32. The CPU reference computes each affine dot product in ascending input-feature index using a binary64 accumulator, adds the Float32 bias, then rounds once to Float32 before activation; activation outputs are rounded to Float32. This is the specified CPU inference order. For attention, compute each tile/query dot product in ascending feature index using a binary64 accumulator, divide by `sqrt(32)`, and round the scaled logit to Float32. Subtract the exact maximum unmasked tile logit, compute each exponential and round it to Float32, sort those exponential values in ascending numeric order, sum in binary64, and round the denominator to Float32. Divide each exponential by that denominator and round each attention weight to Float32. Multiply each weight by its tile-embedding channel and round each product to Float32. For every tile-axis reduction, sort the participating finite Float32 scalar values in ascending numeric order before summing in binary64, then round the result to Float32. Apply this to masked means, attention-softmax denominators, and each channel of attention-weighted sums. Masked maxima use the exact maximum. This canonical reduction order makes pooling independent of tile storage order. Candidate softmax uses the same max-subtract, sorted-denominator reduction. GPU inference may use backend-native Float32 arithmetic but must meet the numeric drift and semantic agreement thresholds below; CPU inference remains the reproducible reference.

Serialize a deterministic sequence of named `Float32Array` tensors. Tensor names, shapes, activations, and order belong to the Schema 1 manifest. Treat the roughly 25,000-parameter / 100 KB figure as a planning estimate only; freeze and test the exact parameter count in the manifest. Parameter count must not depend on tile or player count.

### Frozen Schema 1 Manifest

#### Context Payloads and Candidate Encoding

Every decision has a two-value `tradeCardTransfer` payload: `log1p(cardCountGivenByDecidingSeat)` and `log1p(cardCountReceivedByDecidingSeat)`. Both values are zero outside respond-to-trade decisions. The values describe the current offer from the deciding seat's perspective and are separate from the per-tile `trade transfer` feature. Counts are finite nonnegative integers before normalization. Project the two values through a shared `2 -> 16 ReLU` layer and add the result to the selected context embedding. Deck IDs and card indices are excluded.

Candidate representation is shared as follows:

| Candidate family | 32-value candidate embedding |
| --- | --- |
| Tile action | The shared tile embedding, plus the selected operation embedding in the scorer. |
| Trade counterparty | ReLU projection of that candidate's six seat features (active mask, deciding-seat flag, cash, jail-card count, in-jail flag, jail turns); the candidate deciding-seat flag is zero. |
| Trade property | Shared tile embedding plus the learned transfer-direction embedding. |
| Trade jail card | One shared generic jail-card embedding plus the learned transfer-direction embedding. Each physical card is a separate candidate, including copies from the same deck. |

The four-operation vocabulary and embedding row order are `build`, `mortgage`, `unmortgage`, `sellImprovement`. The jail-card embedding has one row for a generic get-out-of-jail-free card. Transfer-direction embedding row order is deciding seat gives, deciding seat receives. Tile-action score is `dot(tileEmbedding, candidateQuery) + dot(operationEmbedding[operation], candidateQuery) + operationBias[operation]`. Counterparty score is `dot(seatCandidateEmbedding, candidateQuery)`. Trade-asset logit is `dot(assetCandidateEmbedding, candidateQuery) + tradeAssetBias`. The candidate query is a shared linear projection of the trunk with no activation. Every scorer dot product accumulates in ascending feature index using binary64 and rounds once to Float32; evaluate each displayed addition left to right, rounding each intermediate sum to Float32. There is no candidate-specific parameter, tile ID, group ID, storage index, label, color, or candidate-list position in a score.

Candidate-key bytes are canonical and independent of IDs and list order. Encode ASCII `G6K1`, followed by one byte each for family (`0` tile action, `1` counterparty, `2` trade asset), operation (`0` build, `1` mortgage, `2` unmortgage, `3` sellImprovement, `255` not applicable), transfer direction (`0` deciding seat gives, `1` deciding seat receives, `255` not applicable), and descriptor kind (`0` tile, `1` generic jail-free card, `2` seat). A tile descriptor appends its 50 normalized features as little-endian IEEE-754 Float32 values. A jail-card descriptor appends the holder's original one-based seat ordinal as one byte followed by the copy ordinal as uint32 little-endian. The copy ordinal is assigned within the multiset of identical cards and affects only candidate-keyed sampling, never candidate score. A seat descriptor appends its original one-based seat ordinal as one byte followed by its six normalized seat features as little-endian Float32 values. Canonicalize negative zero to positive zero; non-finite descriptor values are invalid. No variable-length text is present. The candidate seed derivation below prefixes these bytes with their byte length as uint32 little-endian. Generic cards with the same holder and direction have identical model scores. Their copy ordinals make candidate-keyed samples independent; assign ordinals to the multiset of identical held cards, never to deck IDs or input list positions. Reordering physical held-card IDs does not change the semantic sampled subset.

Initialize one `candidateChoiceOrdinal` to zero at the start of each match policy-action stream. Before each candidate-choice head invocation, assign its current value to that invocation and increment it once, regardless of candidate-set size or ordering. The ordinal advances across all policy decisions in that match and is not reset between turns. Within a decision, invocation order is jail categorical; tile-action selection; trade-counterparty categorical; trade-asset inclusion. A trade-asset inclusion pass consumes one ordinal shared by all asset candidates in that pass, not one ordinal per asset. Only heads used by that context are invoked. A masked or empty head is not invoked and consumes no ordinal. Jail categorical keys use family `3`, operation/direction `255`, descriptor kind `4`, and one final option byte: `0` use a generic jail-free card, `1` roll, `2` pay bail. Candidate keys therefore distinguish all legal semantic alternatives without relying on their array position.

#### Output Heads and Sharing

All dense output heads read the 64-value trunk and include a bias. Matrix shapes below are `[out, in]`; embedding shapes are `[entries, width]`. Output order is frozen:

| Context | Head tensor/output order | Activation and mask |
| --- | --- | --- |
| Acquire | `head.acquire` (1) | Sigmoid Bernoulli buy; engine legality mask. |
| Auction | `head.auction` (1) | Sigmoid available-cash fraction; round to integer, passing for zero, illegal, or at/below-current-bid. |
| Jail | `head.jail` (3): use generic jail-free card, roll, pay bail | Masked softmax. Roll is always legal; card use is masked when none are held and bail when unaffordable. |
| Property management | `head.propertyGates` (3): build, mortgage, unmortgage | Independent sigmoid Bernoulli gates, legality-masked before sampling; score the resulting legal `(operation, tile)` candidates with the shared operation candidate scorer. |
| Debt resolution | `head.debtGates` (2): sell improvement, mortgage | Independent sigmoid Bernoulli gates, legality-masked before sampling; score the resulting legal `(operation, tile)` candidates with the shared operation candidate scorer. |
| Propose trade | `head.tradePropose` (1), `head.tradeCash` (1) | Sigmoid initiate gate; tanh signed cash fraction. The initiate gate is masked unless at least one eligible counterparty has at least one transferable asset. |
| Respond to trade | `head.tradeRespond` (2): accept, counteroffer | Independent sigmoid Bernoulli gates. Sample counteroffer only after a non-accept decision and only when a counteroffer is legal under the depth limit and has transferable assets; otherwise reject/no-op. |
| Shared choice | No additional dense output tensor | Candidate query scores eligible counterparties and tile actions as specified above; masked softmax/Gumbel-max for categorical choice. Trade assets use one shared masked sigmoid Bernoulli logit per candidate. |

For trade construction, select the counterparty before scoring assets. A response uses the original proposer as its counterparty. The trade-asset bias is shared across every property/card and both transfer directions; there is no per-asset output tensor or asset-count cap. Candidate gates and choices are masked before sampling. If selected assets are empty, decline/no-op rather than emit a cash-only offer. The signed cash fraction is interpreted from the new offer initiator's perspective: nonnegative values offer cash, negative values request cash, with the bounds and rounding already specified above.

#### Initializer and Random Draw Order

Use the PRNG, seed derivation, open-interval uniform, and Box-Muller normal definitions below. Initialize one normal stream with `deriveSeed(masterSeed, "init")`; begin with an empty cached-normal slot. For each matrix weight, draw standard normals in row-major order and multiply by its specified standard deviation: use He-normal `sqrt(2 / fanIn)` for `tile.W1`, `tile.W2`, `context.tradeCard.W`, `trunk.W1`, `trunk.W2`, and `candidate.seat.W`; use Xavier-normal `sqrt(2 / (fanIn + fanOut))` for `attention.W`, every `head.*.W`, and `candidate.query.W`. Initialize every embedding tensor (`context.embedding`, `candidate.operation.embedding`, `candidate.jailCard.embedding`, and `candidate.direction.embedding`) from a zero-mean normal with standard deviation `0.05`. Initialize every bias tensor to zero. `fanIn` and `fanOut` are the matrix input and output dimensions from the named tensor shape.

Set each initial diagonal ES scale per parameter as follows: matrix weights use `0.1` times that matrix's initializer standard deviation; embedding parameters use `0.005`; bias parameters use `0.01`. These scales are Float64 values. Set each initial `logSigma` to the natural logarithm of its initial scale. These formulas are the complete mean and scale initializer contract for every tensor in the manifest.

For each matrix-weight and embedding tensor in manifest order, consume normal draws in row-major element order; bias tensors consume no initializer random draws. Compute normal samples and scale multiplication in binary64, then convert each initialized value to Float32 at assignment. Parameter-noise vectors use the same tensor and row-major order, including all bias coordinates. The exact initializer and parameter-noise outputs for the golden seed `masterSeed = 1` are part of the required deterministic tests.

## Actions and Legality

Apply legality masks to Bernoulli gates, categorical options, trade-asset inclusion, and tile candidates before sampling. The game engine remains the final validator. Training rollouts use the seeded action-sampling rules below; normal gameplay uses deterministic 0.5 Bernoulli thresholds and argmax. Resolve equal candidate scores lexicographically by a canonical semantic feature/action key, independent of tile IDs and candidate-list positions. Identical keys are exchangeable, and candidate reordering preserves the semantic action distribution.

| Context | Heads and action |
| --- | --- |
| Acquire | Bernoulli buy/decline for the landed property. |
| Auction | Scalar fraction of available cash for bid. Convert to an integer; zero, illegal, or at/below-current-bid amounts pass. |
| Jail | Three-way categorical: use a generic get-out-of-jail-free card, roll, or pay bail. Mask card use when no card is held and mask unaffordable bail; roll is always legal. If card use is selected, the engine deterministically chooses one held physical card. |
| Property management | Bernoulli build, mortgage, and unmortgage gates. Shared masked candidate scorer selects a legal `(action, tile)` pair; no-op if none. Apply one improvement action and re-encode after state mutation. |
| Debt resolution | Bernoulli sell-improvement and mortgage gates, followed by shared masked candidate scoring over legal `(action, tile)` pairs; no-op if none. Re-encode after mutation; bankruptcy rules remain authoritative. |
| Propose trade | Bernoulli initiate/decline; on initiate, generate an offer using the trade-selection procedure below. |
| Respond to trade | Bernoulli accept; when not accepted, Bernoulli counteroffer versus reject. A counteroffer uses the same trade-selection procedure with incoming trade context and the existing counteroffer-depth limit. |

### Trade Offer Selection

Initial offers and counteroffers use the same selection procedure. First select an eligible active counterparty with a masked categorical choice. Then score all eligible assets in both directions in parallel and independently select each with its masked Bernoulli output. There is no asset-count or per-direction property-count limit. The candidate set is the complete set of assets the deciding player and selected counterparty may legally transfer under the game engine: properties that can be traded under current property/building rules, plus each physical get-out-of-jail-free card the current holder owns when the recipient can receive it. Each physical card is independently selectable. Mortgage status alone does not exclude a property unless the engine's trade rules make it ineligible. Candidate keys and features use semantic attributes rather than IDs or storage order.

The offer contains one signed integer cash amount. Positive means cash offered by the offer initiator; negative means cash requested from the recipient. The policy emits a signed fraction `f` in `[-1,1]`: for `f >= 0`, cash is `round(f * initiatorCash)`; for `f < 0`, cash is `-round(-f * recipientCash)`. Every integer amount between zero and the applicable current cash balance is representable. The amount must pass the engine's cash-availability checks. The current engine requires at least one property or jail card in an offer, so a cash-only or otherwise empty offer is masked to decline/no-op. The engine remains the final validator; malformed offers become decline/no-op. Counteroffers retain the existing depth limit.

Tax resolution uses the engine's pay-the-lesser rule. Deck contents are excluded from observations; card effects appear in the next state.

## Training: Diagonal OpenAI-ES

Maintain a mean parameter vector `theta` and one diagonal Gaussian scale per parameter, represented by `logSigma`. The default is `P = 16` seeded noise vectors `epsilon_j ~ N(0,I)` and 32 antithetic policies `theta_j+ = theta + sigma * epsilon_j` and `theta_j- = theta - sigma * epsilon_j`. The lower-cost CPU profile uses `P = 8` and 16 policies. Let `u_j+` and `u_j-` be their rank utilities. Compute both gradients from the same pre-update `theta` and `sigma = exp(logSigma)`:

```text
gTheta[i] = sum_j ((u_j+ - u_j-) * epsilon_j[i]) / (2 * P * sigma[i])
gLogSigma[i] = sum_j ((u_j+ + u_j-) * (epsilon_j[i]^2 - 1)) / (2 * P)
```

Maintain independent Adam first/second moments for `theta` and `logSigma`. Use `beta1 = 0.9`, `beta2 = 0.999`, `epsilonAdam = 1e-8`, `thetaLearningRate = 0.01`, and `logSigmaLearningRate = 0.005`. For each vector, update moments in parameter serialization order using `m = beta1*m + (1-beta1)*g` and `v = beta2*v + (1-beta2)*g*g`; apply bias correction at step `iteration + 1`, and perform ascent: `parameter += learningRate * mHat / (sqrt(vHat) + epsilonAdam)`. Update `logSigma` from its gradient, then clamp `exp(logSigma[i])` to `[0.1, 2] * initialSigma[i]` and store the logarithm. Use Float64Array and IEEE-754 binary64 arithmetic for `theta`, `sigma`, `logSigma`, initial scales, noise, fitness/gradient accumulation, and Adam moments. Generate each candidate by calculating `theta +/- sigma*epsilon` in binary64 and assigning each result to the manifest's Float32Array tensor before inference; candidate evaluation therefore always uses Float32 parameters. After initialization, promote Float32-initialized means into Float64 training state. Persist and restore training vectors as Float64Array with exact values. Non-finite fitness or gradient values fail the update visibly without committing a partial update.

#### Deterministic Randomness and Update Order

All seed inputs are unsigned 32-bit integers; iteration, pair, and match indices are zero-based. Derive each stream seed by starting FNV-1a at `2166136261`, feeding the ASCII bytes of its domain tag followed by a zero byte, then feeding `masterSeed` and each tuple integer as four little-endian bytes. For every byte `b`, update `hash = Math.imul(hash ^ b, 16777619) >>> 0`. Finalize with `hash ^= hash >>> 16; hash = Math.imul(hash, 0x7feb352d); hash ^= hash >>> 15; hash = Math.imul(hash, 0x846ca68b); hash = (hash ^ (hash >>> 16)) >>> 0;` This is the complete `deriveSeed(masterSeed, tag, ...tuple)` rule.

Each stream uses Mulberry32: on each draw set `t = state = (state + 0x6D2B79F5) >>> 0`; then `t = Math.imul(t ^ (t >>> 15), t | 1); t ^= t + Math.imul(t ^ (t >>> 7), t | 61);` and return `(t ^ (t >>> 14)) >>> 0`. Convert a `uint32` draw to an open-interval uniform as `(draw + 0.5) / 4294967296`. Generate standard normals with Box-Muller: consume uniforms `u1`, then `u2`; return `sqrt(-2 * ln(u1)) * cos(2*pi*u2)` and cache `sqrt(-2 * ln(u1)) * sin(2*pi*u2)` as the next normal. Draw parameter noise in manifest tensor order and row-major element order, consuming cached normals before generating another pair.

Initialize the mean policy and initial scales only as specified in the frozen manifest. Initialize both Adam moment pairs to zero. Tensor order and fan-in/fan-out are part of the Schema 1 manifest.

Derive streams using these exact tuples: perturbation `(masterSeed, "noise", iteration, pair)`; game `(masterSeed, "game", iteration, pair, match)`; opponent lineup `(masterSeed, "league", iteration, pair, match)`; and policy actions `(masterSeed, "action", iteration, pair, match)`. Scenario selection uses one stream per coverage cycle, seeded from the cycle's starting slot as specified below; do not derive a separate scenario permutation stream per update or match. Scenario assignments are shared by all candidates; game, lineup, and action streams are shared by the plus/minus policies within each pair. Aggregate results in task-ID order `(iteration, pair, sign, match)`, with plus before minus, independent of worker completion order.

For candidate-choice sampling, derive a candidate seed by starting the same FNV-1a hash, feeding ASCII `candidate` plus a zero byte, the action seed and zero-based candidate-choice ordinal as little-endian uint32 values, then the byte length of the canonical semantic key as uint32 and the key's canonical bytes; apply the same finalizer. Seed a fresh Mulberry32 stream from that result and use its first open-interval uniform in Gumbel-max, `logit - ln(-ln(u))`. For candidate-keyed Bernoulli sampling, use the same derivation with tag `candidate-bernoulli` and select exactly when the first uniform is less than the candidate probability. Canonical key bytes are defined by the Schema 1 candidate-key manifest and use semantic features/actions rather than IDs or list positions. Identical keys receive identical random values and are exchangeable. Other stochastic heads consume action-stream draws in fixed context/head order from the manifest.

For every non-candidate Bernoulli output, rollout sampling draws one uniform from the match action stream in this fixed within-decision order: acquire `buy`; property `build`, `mortgage`, `unmortgage`; debt `sellImprovement`, `mortgage`; propose-trade `initiate`; respond-trade `accept`, then `counteroffer` only when the offer was not accepted and a counteroffer is legal. Only outputs invoked in the current context draw; legality masks are applied before drawing. Select true exactly when `u < p`. Candidate Bernoulli outputs use the candidate-keyed rule above. Categorical outputs use Gumbel-max with one candidate-keyed uniform per legal semantic choice and select the greatest perturbed logit. Candidate-choice ordinals are assigned once per categorical/candidate-selection head invocation in policy decision order, independently of candidate-set size or ordering. Scalar outputs are deterministic head values and consume no action-stream draw. Every stochastic game-engine operation uses the match `game` stream, never ambient `Math.random`: shuffle every deck in ascending UTF-8 bytewise deck-ID order using descending Fisher-Yates (`i = length - 1` to `1`, `j = floor(u * (i + 1))`); for each die roll, draw die one then die two, each as `1 + floor(6u)`. No other game operation consumes randomness. Gen5 and StrategicAI opponents use the frozen explicit profiles and must not invoke random profile/parameter generation. Deterministic gameplay consumes no random values: Bernoulli uses `p >= 0.5`; categorical/candidate outputs use maximum probability/score with lexicographic semantic-key tie-breaking.

Rank-normalize the `C = 2P` candidate fitnesses by sorting ascending and assigning average zero-based ranks to exactly tied fitness values. Convert each rank `r` to utility `u = (r - (C - 1)/2) / (C - 1)`; for default `C = 32`, this is `(r - 15.5) / 31`. The resulting utilities have mean zero, with higher fitness receiving higher utility. A non-finite fitness fails the update visibly. Compute both gradients from the same pre-update `theta`, `sigma = exp(logSigma)`, and utilities. Update Adam moments in parameter serialization order, use standard bias correction at update number `iteration + 1`, and apply ascent (`parameter += learningRate * mHat / (sqrt(vHat) + 1e-8)`). Update `logSigma` using its own learning rate and moments, then clamp `exp(logSigma)` to `[0.1, 2]` times its initial scale and store the resulting logarithm. Use the specified values for initial runs; benchmark alternatives separately.

Each policy gets `R` seeded matches per update, each capped at 60 active-player turns (one `play()` turn-count increment); defaults are `R = 4`, and the lower-cost CPU profile uses `R = 2`. Build the training-condition catalogue in this order: training-board ordinal, player count ascending 2-8, `auctionEnabled` false then true, `freeParkingTaxes` false then true, and deciding-seat ordinal ascending from 1 through player count. For `N` catalogue entries, flatten match slots as `slot = R * iteration + match`; `cycle = floor(slot / N)` and `position = slot mod N`. The first slot of cycle `c` is `cycleStartSlot = c * N`; derive its update and match as `floor(cycleStartSlot / R)` and `cycleStartSlot mod R`. At the start of each cycle, generate one Fisher-Yates permutation of the catalogue using Mulberry32 seeded by `deriveSeed(masterSeed, "scenario", floor(cycleStartSlot / R), cycleStartSlot mod R)`. Shuffle from `i = N - 1` down to `1`, drawing the open-interval uniform `u` and setting `j = floor(u * (i + 1))`, then swapping entries `i` and `j`. Assign catalogue entry `permutation[position]` to that match slot. This covers every board/player-count/rule/seat combination exactly once per complete cycle, and all candidates in an update see the same `R` assigned scenarios. The pair-specific league stream chooses each opponent seat in ascending original seat ordinal: draw one uniform to select a pool with normalized probabilities 50% archive, 25% champions, and 25% baselines, then one uniform to select an entry uniformly with replacement within that pool. If a pool is empty, renormalize the remaining pool weights before drawing. The chosen lineup is identical for both signs of a pair. The baseline pool contains exactly two entries, sampled equally: Gen5 with profile `Tactician` and explicit parameter values equal to the means in `AIGen5.ParameterGenerator.PARAM_SPEC` (`reserveSafetyMargin: 1.15`, `batchBuildMinROI: 0.22`, `unmortgageROIThreshold: 0.12`, `tradeReofferWealthDeltaPct: 0.20`, `tradeReofferTurnGap: 8`, `auctionBlockPremium: 1.3`); and StrategicAI with profile `Balanced`. Construct no baseline through random profile or parameter generation. After each update, order the `2P` evaluated policies by stable task ID and retain the latest 32 for the next update's archive. Keep the 16 highest-validation-score distinct past champions; policies are duplicates only when their tensor values have identical IEEE-754 Float32 bytes serialized little-endian in manifest order. Break champion-score ties by earlier creation iteration, then unsigned lexicographic comparison of those same serialized bytes. After each match, average tied ranks and compute placement score `(playerCount - 1 - rank) / (playerCount - 1)`. Win score is 1 for sole first, `1 / numberTiedForFirst` for a first-place tie, and 0 otherwise. Fitness is `0.75 * mean placement score + 0.25 * mean win score`. Rank-normalize candidate fitness for the ES update. Derive perturbations from `(masterSeed, iteration, pair)` and rollout streams from `(masterSeed, iteration, pair, match)`. Aggregate by stable task ID so worker completion order cannot change an update.

Freeze the opponent league before each update from the latest completed update's candidate archive (50%), past champions (25%), and fixed Gen5/StrategicAI baselines (25%); renormalize when a group is empty. Candidates evaluated in an update enter the league archive for the next update. Store best candidates and their evaluation metadata. All candidates in one update use the same scenarios and each antithetic pair shares its opponent lineup. Rotate a deterministic balanced schedule so every training board x player count (2-8) x rule-setting combination is equally represented over a complete coverage cycle. Validate champions against the full Board Evaluation Set, including held-out boards.

## Runtime and Resource Budget

At 52 tiles, the shared tile encoder costs approximately 0.14 million multiply-accumulates per decision; attention, trunk, and batched candidate scores bring the estimate to roughly 0.15-0.2 million. Reuse one tile encoding per unchanged observation and batch candidate scores. Reuse typed-array scratch storage and bound concurrent matches. Workers return scalar fitness/compact diagnostics; the ES coordinator stores diagonal scale vectors rather than dense covariance matrices. Enforce a default configurable **64 MiB per active match** budget over tile-feature arrays, tile activations, attention/pooling scratch, candidate-score scratch, and policy inference scratch. Compute the required typed-array bytes from actual tile and legal-candidate counts before allocating any match scratch; reject visibly before allocation if the budget would be exceeded. Do not count the JavaScript object graph or engine game state toward this specific typed-array budget; measure and report those separately. With four workers, the default aggregate typed-array match budget is at most 256 MiB, excluding coordinator and engine state.

Use the reference target of a six-core, 3.5 GHz midrange Ryzen 5 with an 8 GB NVIDIA GPU available. Keep game simulation and ES orchestration on the CPU. The CPU policy evaluator is the reference and fallback; an optional WebGPU evaluator may batch policy inference across concurrent matches when the backend is available and profiling shows an end-to-end benefit. Do not move game rules or match state to the GPU. Set initial defaults to at most four simulation workers, 16 antithetic pairs, four 60-active-player-turn rollouts per policy (128 matches/update), and 100-active-player-turn validation matches. Compare CPU-only and hybrid runs on 52 tiles/eight players, including batching, dispatch, transfer and synchronization overhead. The fixed GPU comparison corpus contains at least 11 observations for every combination of seven contexts, tile counts 28/40/52/64/100, player counts 2-8, and all four auction/Free Parking rule combinations: 10,780 observations total. Cover legal and empty candidate masks where applicable. Before GPU inference may be enabled for training, require maximum absolute drift of every unmasked head output and candidate score at most `1e-5`, semantic action agreement at least `99.9%`, and byte-identical repeated outputs within each backend for identical inputs/parameters. If any criterion fails, GPU training remains disabled and CPU is the reference. Also report wall time per match/update, peak CPU/GPU memory, policy evaluations per second, worker utilization, drift, and action agreement. Keep GPU availability optional and provide a configurable lower-cost CPU profile of eight pairs, two rollouts per policy, and two workers; its default typed-array match budget remains 64 MiB per worker unless configured otherwise.

For memory planning, a 52-tile observation plus two 32-wide activation buffers is about 24 KB in Float32 form; 25,107 policy parameters use 100,428 bytes (about 98 KiB). The ES coordinator keeps seven Float64 parameter-sized vectors (`theta`, `logSigma`, `initialSigma`, and first/second Adam moments for each of `theta` and `logSigma`), 1,405,992 bytes total (about 1.34 MiB), plus noise/scratch buffers. Hold at most one active match and candidate policy per worker; stream matches through the worker pool. These estimates exclude game-state and JavaScript object overhead and must be checked by profiling.

There is no semantic maximum tile count. Enforce a configurable tile/activation memory budget at match/training boundaries and fail visibly before allocation rather than truncate. Test 28, 40, 52, 64, and 100 tiles. Operational budget failures are not schema incompatibilities.

## Persistence and Coverage
`iteration` is the zero-based index of the next update to execute. A new run starts at 0; commit update `i` atomically with `iteration = i + 1` and `nextScenarioSlot = rolloutsPerPolicy * (i + 1)`. Never checkpoint a partially aggregated update.

Persist through IndexedDB database `monopoly-gen6-schema1`, database version 1, with object stores `policies` (key path `policyId`) and `trainingState` (key path `stateId`). The `policies` store has at most one record, with `policyId: "active"`; it contains the latest validated playable champion, never an unvalidated mean. Its exact fields are `format: "monopoly-gen6-policy"`, `schemaVersion: 1`, `policyId`, `tensors` (ordered `{name, shape, values}` records; `values` is a Float32Array), `validation`, and `coverage`. `validation` contains `boardSetVersion`, `evaluatedIteration`, aggregate `placementScore` and `winScore`, and one result per held-out condition with `boardKey`, `playerCount`, `auctionEnabled`, `freeParkingTaxes`, `wins`, `tiesForFirst`, `meanRank`, `placementScore`, and `winScore`. `coverage` contains `scheduleVersion: 1`, ordered `trainingBoardKeys`, ordered `heldOutBoardKeys`, completed condition records `{boardKey, playerCount, auctionEnabled, freeParkingTaxes, seatOrdinal, matchCount}`, and over-budget records `{boardKey, tileCount, budgetBytes, status: "resource-rejected"}`. A resumable record has `format: "monopoly-gen6-training-state"`, `schemaVersion: 1`, `stateId: "active"`, `iteration`, `trainingProfile: {pairsPerUpdate, rolloutsPerPolicy, maxTurnsPerMatch, validationMatchesPerCondition, validationTurnsPerMatch, inferenceBackend}`, theta tensors, diagonal `logSigma`, `initialSigma`, separate Float64 theta/logSigma Adam first/second moments, `masterSeed`, `nextScenarioSlot`, `boardSetVersion`, the latest-32 candidate archive in task-ID order, and up-to-16 distinct champion records. `trainingProfile` is exactly one of `{pairsPerUpdate: 16, rolloutsPerPolicy: 4, maxTurnsPerMatch: 60, validationMatchesPerCondition: 4, validationTurnsPerMatch: 100, inferenceBackend: "cpu"}` or the lower-cost `{pairsPerUpdate: 8, rolloutsPerPolicy: 2, maxTurnsPerMatch: 60, validationMatchesPerCondition: 4, validationTurnsPerMatch: 100, inferenceBackend: "cpu"}` initially; accepted WebGPU training records use the same numeric profile and `inferenceBackend: "webgpu"`. Require `nextScenarioSlot = rolloutsPerPolicy * iteration`. A resumed run must match its saved profile, seed, and Board Evaluation Set version; worker count may change because results aggregate in stable task-ID order. To change pair/rollout profile, master seed, or inference backend, start a new training state rather than silently continuing the saved optimizer/archive. Candidate/champion records contain ordered tensors plus task/creation IDs, fitness or validation score, and evaluation metadata. The `policies/active` record and `trainingState/active` record are written atomically in one read-write transaction after a complete update; if no validated champion exists yet, the policy record may be absent while the training checkpoint is committed. Only complete-update checkpoints are resumable.

Validate exact formats, schema version, tensor names/shapes/counts, finite parameter and optimizer values, positive finite scales, unsigned seeds, archive/champion metadata, and coverage records before use. Compatibility is determined by exact `schemaVersion`; same-version payload validation does not redefine schema compatibility. Detect legacy localStorage keys `gen6Population` and `gen6Champion` by enumerating key names with `length`/`key(index)` only; if either exists, report that legacy NEAT data is unsupported and leave it untouched. Never call `getItem` for those keys, parse their values, import, migrate, or warm-start them. Do not inspect or modify the unrelated `gameHistory` key. New Schema 1 saves use only the new IndexedDB database and records. If IndexedDB is unavailable or quota/write fails, surface the error and do not report a successful checkpoint. Provide an injectable IndexedDB-compatible adapter for deterministic Node tests. Save, reload, fully validate, compare deterministic inference, and verify that the next seeded ES update is byte-identical.

The Board Evaluation Set includes every registered compatible built-in edition within the configured resource budget plus seeded synthetic boards with varied tile count, group structure, kinds, and economics. Every in-budget built-in edition participates in policy-update training; no in-budget built-in edition is held out from training. Use metadata-only stable keys `edition:<editionId>` for built-ins and `synthetic:<fixtureName>` for synthetic boards; these keys never enter policy observations or candidate scores. Maintain an explicit ordered evaluation manifest containing each board key and role; synthetic entries also contain the fixture name, generator version, and seed. Include every in-budget built-in in `trainingBoardKeys`; partition synthetic fixtures into training and held-out sets, with at least one in-budget synthetic fixture in each set. Held-out synthetic boards are excluded from policy-update scenarios and are used only for champion validation.

The evaluation manifest is the exact object `{scheduleVersion: 1, memoryBudgetBytes, entries}`. `entries` is ordered by unsigned lexicographic order of each `boardKey`'s UTF-8 bytes. Every entry has `boardKey` and `role`; synthetic entries additionally have exactly `fixtureName`, `generatorVersion`, and unsigned 32-bit `seed`. Built-in entries have no other fields. The roles are `training-edition`, `training-synthetic`, `held-out-synthetic`, or `resource-rejected`. For every role except `resource-rejected`, the key prefix must agree with its edition/synthetic role; `resource-rejected` may use either prefix. The manifest excludes `boardSetVersion` itself. Compute `boardSetVersion` as lowercase hexadecimal SHA-256 of UTF-8 RFC 8785 JSON Canonicalization Scheme (JCS) output for this object. The same board-key ordering determines board ordinals. Changing the memory budget, role assignment, synthetic fixture name, generator version, or seed changes the hash. Built-in board revisions are intentionally not represented in this manifest and do not independently change its hash. Include over-budget registered boards in the manifest and coverage, but not in training or validation; record their visible resource-rejection status. The board keys, fixture seeds, budget, and training/holdout roles are frozen for the duration of a run.

Cover training boards across all player counts 2-8 and all four auction/Free Parking rule combinations over a complete balanced cycle. After each update, rank its `2P` candidates by training fitness, breaking ties by task ID, and fully validate the top four (or all candidates when fewer than four) before considering champion promotion. For each candidate, validate on every in-budget registered built-in edition and every held-out synthetic board across player counts 2-8 and all four rule combinations, with four matches per condition capped at 100 active-player turns. Validation runs use fixed scenarios disjoint from training rollouts and the same seeds, seats, and baseline opponents for every candidate. Validation seeds derive as `deriveSeed(masterSeed, "validation", boardOrdinal, playerCount, auctionEnabledBit, freeParkingTaxesBit, replicate)`; replicate is zero-based. Assign candidate seat `(replicate mod playerCount) + 1`. Enumerate other active seats in ascending original seat ordinal; for zero-based opponent ordinal `q`, choose Gen5 when `(q + replicate) mod 2 = 0` and StrategicAI otherwise. Score each condition as the mean of its four `0.75 * placement + 0.25 * win` match scores, then average condition scores equally for champion validation. Report built-in edition validation and held-out synthetic validation separately. Combine newly validated candidates with prior champion records, deduplicate by exact Float32 tensor bytes, and retain the 16 highest validation scores using the specified stable tie break.

The canonical JSON used for `boardSetVersion` is RFC 8785 JCS applied to the exact manifest object defined above. Evaluation-manifest invalidation tests cover changed roles, synthetic fixture metadata/seeds, and memory budgets; built-in content revisions are intentionally not represented by this Schema 1 manifest.

### Validation Persistence Clarification

This paragraph is normative and replaces the earlier persistence wording that specified one validation result per held-out condition. The `validation` object contains one result per validation condition across all in-budget registered built-in editions and all held-out synthetic boards. Each result contains `boardKey`, `boardRole` (`training-edition-validation` or `held-out-synthetic-validation`), `playerCount`, `auctionEnabled`, `freeParkingTaxes`, `wins`, `tiesForFirst`, `meanRank`, `placementScore`, and `winScore`. Built-in edition validation uses independent fixed validation scenarios; held-out synthetic boards are never used for training. Coverage reports training condition records and validation condition records separately, in board-key order and then the catalogue condition order.

## Required Tests

The cases below are mandatory conformance gates. The current pre-alpha NEAT runtime is not an implementation target and its tests do not satisfy these cases. Runtime-dependent cases remain pending until the Schema 1 runtime is implemented in Phase 6; pending cases must not be reported as passing.

- **S1-01 Observation:** Exact 50-feature tile records with a single generic card-kind feature; variable nonnegative jail-card counts and transfer counts use unclamped `log1p`; verify seat/global shapes, optional tax-rate encoding, and named tensor/parameter counts.
- **S1-02 Effective rules:** Effective Board rule values encode correctly; valid per-game overrides are validated, reflected in Gen6 observations, isolated between Games, and never mutate or persist to the edition base rules.
- **S1-03 Initialization and inference:** Exact tensor initialization means/scales and golden-seed outputs, plus CPU attention logits, masked softmax, and weighted-pooling results under canonical reduction order.
- **S1-04 Invariance and variable boards:** Shared weights across tiles; identical output under storage reorder and ID relabeling with graph semantics preserved; fixed parameter count and finite outputs across 28/40/52/64/100-tile boards.
- **S1-05 Candidate equivariance:** Candidate-action equivariance under candidate-list reorder; identical legal candidate distributions by semantic features and storage-order-independent tie handling.
- **S1-06 Legality and fail-closed behavior:** Illegal actions are absent after masking; empty masks, jail fallbacks, bids, debt actions, and trade decoding fail closed.
- **S1-07 Trade semantics:** Trade subset permutation invariance, independent selection of every physical generic jail card, copy-key invariance under held-list reordering, variable transfer counts, no asset-count cap, duplicate prevention, integer cash bounds/conversion, jail-card ownership/receivability, property/building restrictions, empty-offer rejection, and counteroffer-depth limit.
- **S1-08 Deterministic training:** Seeded ES perturbations, antithetic fitness scenarios, gradients/updates, fitness aggregation, league sampling, coverage cycles, and worker-order independence.
- **S1-09 Board Evaluation Set:** Evaluation-manifest ordering and hashing, training coverage of every in-budget built-in, disjoint synthetic holdouts, and evaluation-revision invalidation.
- **S1-10 Resource and backend profiles:** 52-tile/eight-player end-to-end CPU-only and optional WebGPU-inference performance and memory profiles on the reference hardware; report backend overhead, seeded repeatability, numeric output drift, and semantic action agreement against thresholds defined before enabling GPU training, with configurable resource rejection and a lower-cost CPU profile.
- **S1-11 Persistence and rejection:** Persistence round trip preserves deterministic inference and the next seeded ES update; malformed and legacy data are rejected visibly.
